# 설계 기록

이 문서는 **무엇을 골랐는지보다 무엇을 버렸는지**를 남긴다.
나중에 "왜 이렇게 했지" 싶을 때 같은 길을 다시 헤매지 않기 위함이다.

## 최종 구성

```
www.namsu.kim    Astro           공개 사이트 (SSG + 필요한 곳만 SSR)
admin.namsu.kim  Vite + React    관리자 SPA, Cloudflare Access 뒤
api.namsu.kim    Hono            REST API
                 D1              데이터 (SQLite)
                 R2              이미지/첨부
                 Access          관리자 인증
                 Turnstile       댓글·좋아요 봇 차단
```

전부 Cloudflare Workers. 배포는 GitHub Actions → `wrangler deploy`.

## 검토했다가 버린 것들

### GitHub Pages + 정적 사이트

처음 요구사항은 GitHub Pages 배포였다. 하지만 관리자 페이지·좋아요·댓글은
서버와 DB 를 필요로 하고, Pages 는 정적 파일만 서빙한다.
댓글을 Giscus(GitHub Discussions)로 넘기면 가능했지만
**댓글 작성에 GitHub 계정이 필요해져서** 일반 독자를 받을 수 없다.

### Go 백엔드 + Cloudflare D1

Go 로 API 를 짜고 D1 을 쓰려 했으나, **D1 은 Workers 런타임 바인딩 전용**이다.
외부 Go 서버에서는 REST API 로만 접근 가능한데:

- Cloudflare 전역 API 레이트리밋(계정당 1,200 req / 5분)을 공유한다
- 매 쿼리가 HTTPS 왕복이라 레이턴시가 붙는다
- 커넥션 풀·트랜잭션 개념이 없고 `database/sql` 드라이버도 없다

→ Go 를 쓰려면 Postgres 로 가야 했다.

### 집 노트북 + Cloudflare Tunnel

우분투를 올린 노트북(4GB RAM)에 Go + Postgres 를 두고 Tunnel 로 노출하는 안.
동작은 하지만 감수할 것이 많았다.

- RAM 3.7GB 에 맞춘 Postgres 튜닝
- 노트북 가동률에 사이트가 묶임 → ISR 캐시로 우회하는 추가 설계
- 공개 저장소라 self-hosted GitHub runner 를 쓸 수 없어(포크 PR 이 집 노트북에서 코드를 실행할 수 있다)
  풀 방식 배포 파이프라인을 따로 만들어야 함

월 $5 로 전부 사라지는 복잡도였다.

### Cloud Run + 집 노트북 Postgres

컴퓨트와 DB 를 터널로 갈라놓는 구성. 두 방식의 단점만 합쳐진다.
터널 유지를 위해 `min-instances=1` 이 필요해지는 순간 Cloud Run 무료 티어의
의미가 사라지고, 쿼리마다 20~40ms 가 붙으며, 장애 지점은 둘이 된다.

### Hetzner VPS

월 5천 원대로 4GB RAM 전용 서버를 얻는 안. 가성비는 최고지만
**저가 라인이 EU 리전 전용**이라 한국에서 왕복 250ms 이고, 조사 시점에 품절이었다.

### Express (Workers 위)

2026-08-04 부터 Workers 는 Node.js 호환이 기본 활성화라 Express 도 돈다.
하지만 폴리필 계층을 거치고, D1 바인딩(`env.DB`)을 핸들러로 넘길 구조가 아니라
전역변수 우회가 필요하다. Hono 는 이게 기본 설계(`c.env.DB`)라 Hono 를 골랐다.

### Next.js

프런트를 Next 로 하려 했으나 OpenNext 변환 계층이 필요하고,
API 에서 글을 읽어오는 블로그에는 App Router·Server Actions·ISR 의 이점이 작다.
Astro 는 `@astrojs/cloudflare` 로 네이티브 배포된다. Express 를 버린 것과 같은 이유다.

관리자도 Next 대신 Vite + React SPA 로 갔다. **인증 뒤에 있는 CRUD 화면에 SSR 이 주는 이점이 없다.**

### Supabase

Postgres + Auth + Storage 를 한 번에 주지만 **무료 플랜은 7일 무활동 시 프로젝트가 정지**된다.
개인 블로그에는 현실적인 지뢰다.

## 관리자 인증을 직접 짜지 않는 이유

`admin.namsu.kim` 과 `api.namsu.kim/v1/admin/*` 을 Cloudflare Access 정책으로 감싼다.
Access 가 Google SSO 로 신원 확인을 끝낸 뒤 `Cf-Access-Jwt-Assertion` 헤더에
서명된 JWT 를 실어 보내고, API 는 그 서명만 검증한다.

얻는 것:

- 비밀번호 해싱·세션 관리·2FA 코드가 이 저장소에 존재하지 않는다 (공개 저장소에서 중요하다)
- 관리자 화면이 인증 없이는 네트워크 레벨에서 아예 도달 불가능하다
- 무료다 (50명까지)

전제: **API 의 관리자 경로도 반드시 Access 뒤에 있어야 한다.**
프런트만 막고 API 를 열어두면 의미가 없다.
서버는 여기에 더해 JWT 의 이메일이 허용 목록에 있는지 2차 검증한다.

## 개인정보 최소수집

공개 저장소이기도 하고, 필요 없는 데이터를 들고 있을 이유도 없다.

- **IP 원문을 저장하지 않는다.** 좋아요 중복 방지와 레이트리밋에는
  `sha256(ip + user-agent + 서버 솔트)` 해시면 충분하다.
- **댓글 이메일은 응답에 절대 싣지 않는다.** 답글 알림과 아바타 해시 용도로만 쓰고,
  공개 API 쿼리에서는 아예 SELECT 하지 않는다.
- 로그에 쿼리스트링 값과 IP 를 남기지 않는다.

## 비밀 댓글과 대댓글

두 기능은 서로 얽혀 있어 규칙을 먼저 정하고 만들었다.

- **비밀 댓글의 본문은 서버가 렌더하지 않는다.** 공개 API 가 `authorName` 과 `body` 를
  빈 문자열로 비워 내려보내고, 화면에는 잠금 표시만 나간다.
  글 페이지는 엣지에 캐시되므로 "방문자에 따라 다르게 보여주기"가 성립하지 않는다.
  한 번 캐시에 실리면 그 응답이 다음 방문자에게 그대로 간다.
- **비밀 댓글에 달리는 답글은 서버가 무조건 비밀로 만든다.** 클라이언트가 보내는
  `isSecret` 값은 참고만 하고, 부모가 비밀이면 덮어쓴다. 답글 한 줄만으로도
  원래 질문이 짐작되기 때문이다("네, 그 부분은 ... 입니다").
- **댓글 수는 화면에 보이는 줄 수와 같다.** 승인되고 삭제되지 않은 댓글이면
  비밀 댓글도 센다. 처음에는 "숨긴 게 있다는 사실이 드러난다"는 이유로 뺐는데,
  공개 화면이 비밀 댓글 자리에 잠금 표시를 그대로 그리므로 존재는 어차피 보인다.
  숫자만 빼니 숫자와 화면이 어긋나기만 했다 (`0003_count_all_comments.sql`).
- **답글 깊이는 2단까지.** 모바일에서 들여쓰기가 더 깊어지면 읽기 어렵다.
  공개 화면의 답글 버튼과 서버의 검사가 같은 상수를 쓴다.
- **방문자는 비밀 댓글에 답글을 달 수 없다.** 읽을 수 없는 글에 답글 버튼을 주면
  아무도 읽지 못하는 가지만 생긴다. 비밀 댓글의 답글은 관리자만 단다.

### 비밀 댓글 작성자는 답을 사이트에서 읽지 못한다

로그인이 없으므로 "이 비밀 댓글을 쓴 사람"임을 증명할 방법이 없다.
방문자 해시(`sha256(ip + UA + 솔트)`)로 본인 확인을 흉내낼 수는 있지만,
같은 공유기 뒤에서 같은 브라우저를 쓰는 두 사람이 같은 해시를 갖는다.
비밀이라고 약속한 내용을 남에게 보여줄 위험을 감수할 이유가 없어서 쓰지 않았다.

그래서 비밀 댓글은 **주인에게 보내는 단방향 쪽지**로 설계했다.
답장은 댓글 폼의 (선택) 이메일로 간다 — 관리자가 답글을 달면 그 내용이 메일로 발송된다.
공개 화면에는 잠금 표시 옆에 "답변 완료" 배지만 붙고 내용은 드러나지 않는다.

## 비밀글

비밀번호를 걸면 본문이 잠긴다. 비밀 댓글과 같은 원칙이다 —
**잠긴 내용은 서버가 아예 렌더하지 않는다.** 글 페이지는 엣지에 캐시되므로
"맞힌 사람에게만 다르게 그려주기" 가 성립하지 않는다. 한 번 캐시에 실리면
그 응답이 다음 방문자에게 그대로 간다.

- 공개 상세 API 는 비밀글의 `contentHtml` 을 `null` 로, 요약·표지·메타태그를 비워서 준다.
- 본문은 `POST /v1/posts/:slug/unlock` 이 `Cache-Control: private, no-store` 로만 내려준다.
- 비밀번호는 PBKDF2-SHA256(10만 회) 해시로만 저장한다. 평문은 어디에도 남지 않고,
  해시는 관리자 응답에도 실리지 않는다 (`hasPassword` 불리언만 나간다).
- 한 번 푼 사람에게는 그 글 하나에만 쓰이는 서명 토큰을 준다(24시간).
  브라우저에 비밀번호를 저장하는 것보다 낫다.
- 무차별 대입은 전용 레이트리밋(`RATE_LIMIT_UNLOCK`, 분당 10회)으로 막는다.
  좋아요와 같은 통을 쓰면 한쪽이 다른 쪽 예산을 태운다.

### 목록에 보이는 방식은 글마다 고른다

| 값             | 목록에서                                         |
| -------------- | ------------------------------------------------ |
| `title` (기본) | 제목과 자물쇠만. 요약·표지·읽는 시간은 가린다    |
| `masked`       | "비밀글" 이라고만. 제목·카테고리·태그까지 가린다 |
| `hidden`       | 아예 안 나온다. 직접 링크를 아는 사람만 들어온다 |

가리는 판단은 `toSummary()` 한 곳에서 한다. 목록 화면마다 다시 가리게 두면
새 화면을 만들 때 한 군데를 빠뜨린다.

### 색인

어느 방식이든 **사이트맵·RSS·검색·관련글·이전다음글에서 전부 빠진다.**
`visibility.ts` 의 `indexablePost` 가 그 기준이고, 글 페이지 자체도 `noindex` 다.
목록에서 뺐더라도 링크가 어디엔가 걸리면 크롤러는 따라 들어온다.

`hidden` 으로 두어도 **주소(slug)는 감춰지지 않는다.** 링크를 받은 사람은
주소만 보고 내용을 짐작할 수 있으니, 정말 가리고 싶으면 slug 도 무의미하게 둘 것.

### 비밀글은 댓글을 받지 않는다

본문을 잠가 놓고 그 아래 토론이 공개로 쌓이면 내용이 그대로 짐작된다.
댓글마다 다시 잠금을 확인하는 것보다 아예 받지 않는 편이 확실하다.
잠금을 풀면 댓글도 다시 열린다.

## 방문 통계는 둘 다 선택 가능

`site.cfBeaconToken` 과 `site.gaMeasurementId` 를 관리자 설정에서 넣는다.
비어 있으면 해당 스크립트를 아예 넣지 않는다.

- **Cloudflare Web Analytics** — 쿠키를 쓰지 않아 동의 배너가 필요 없다. 무료.
- **Google Analytics 4** — 쿠키를 심으므로 개인정보처리방침에 수집 사실을 적어야 한다.
  `anonymize_ip` 를 켜서 보낸다.

## 댓글은 승인 없이 바로 공개한다

Turnstile 이 봇을 거르고, 같은 방문자가 5분 안에 같은 내용을 또 보내면 막는다.
그 위에 사람이 하나씩 승인하는 단계까지 두면 방문자는 자기 댓글이 사라진 것처럼
느끼고, 주인은 늘 밀린 큐를 안고 산다. 개인 블로그 규모에서는 값이 안 맞는다.
문제가 되는 것만 사후에 스팸 처리하거나 삭제한다.

`COMMENTS_REQUIRE_APPROVAL` 을 `true` 로 되돌리면 승인제로 돌아간다.
코드는 양쪽을 모두 지원한다.

글 페이지는 엣지에 60초 캐시되므로 방금 올린 댓글이 새로고침으로는 바로 안 보일 수 있다.
그래서 등록 응답에 화면이 그릴 만큼의 값을 실어 보내고, 스크립트가 목록에 끼워 넣는다.
이 마크업은 `CommentItem.astro` 와 같은 모양이어야 한다 — 답글 버튼을 다는 규칙까지 같다.

## 방명록은 댓글과 따로 둔다

`guestbook` 테이블을 새로 만들었다. `comments` 에 `post_id` 를 nullable 로
만들어 겸용할 수도 있었지만, 그러면 트리 조립·깊이 제한·답글 알림·비밀 댓글
마스킹이 전부 "방명록이면 건너뛴다" 분기로 뒤덮인다. 방명록은 글에 붙지 않고
답글도 없어서 그 코드가 통째로 필요 없다.

공유하는 것은 이미 따로 떼어 둔 것들이다 — Turnstile, 레이트리밋, 방문자 해시,
5분 내 같은 내용 재전송 차단, 스팸·삭제·되살리기, 주인 알림 메일.
규칙도 댓글과 같다: 승인 없이 바로 공개하고, 이메일은 공개 응답에서
아예 SELECT 하지 않으며, 작성자 홈페이지 링크에는 `nofollow` 를 붙인다.

## 관리자 편집기는 마크다운 그대로를 다룬다

WYSIWYG 을 붙이지 않았다. 저장되는 값이 마크다운이고 공개 화면은 그것을
**서버에서** 렌더한다. 편집기가 HTML 을 만들기 시작하면 원본과 렌더 결과가
갈라지고, 그때부터는 어느 쪽이 정본인지 알 수 없게 된다.

대신 손이 덜 가도록 세 가지를 붙였다 — 도구 모음, `Cmd/Ctrl + B/I/K` 단축키,
목록·인용 안에서 Enter 를 치면 다음 줄에 같은 표기를 이어주는 것.
미리보기는 `POST /v1/admin/preview` 로 **서버의 렌더러를 그대로** 부른다.
화면에서 따로 렌더하면 실제로 게시될 결과와 미묘하게 달라진다.

편집기가 커서를 옮길 때는 React 가 다시 그린 뒤여야 한다. `value` 를 부모가
들고 있어서, 값을 바꾸자마자 커서를 옮기면 렌더 직후 브라우저가 커서를
맨 끝으로 보내 버린다. 자리를 적어 뒀다가 `useLayoutEffect` 에서 옮긴다.

### 색과 강조는 원시 HTML 없이 넣는다

원시 HTML 을 전부 이스케이프하는 것이 이 렌더러의 안전 불변식이라
`<span style=...>` 같은 걸 허용할 수 없다. 대신 마크다운 확장 둘을 만들었다.

- **알림 상자** — GitHub 의 `> [!NOTE]` 문법. 종류는 다섯 가지 중에서만 고를 수
  있고, 클래스 이름(`md-alert-note`)은 **서버가 만든다.** 사용자가 쓴 문자열이
  클래스에 닿지 않으므로 속성 주입이 성립하지 않는다.
  모르는 종류는 그냥 인용문으로 떨어진다.
- **형광펜** — `==중요==` 를 `<mark>` 로. 표준은 아니지만 관용 표기이고,
  지원하지 않는 곳에서는 `==` 가 글자로 보일 뿐이라 내용을 잃지 않는다.

종류별 색은 테마 토큰으로만 쓴다. winter 에서 흐린 색이 dracula 에서는
밝아지므로, 글자색까지 종류 색으로 칠하면 한쪽 테마에서 반드시 읽기 어려워진다.
테두리와 옅은 배경만 칠하고 제목은 본문 색 + 이모지로 구분한다.

## 알림 메일은 외부 서비스로 보낸다

Cloudflare 의 Email Routing 은 받기만 한다. Email Workers 의 `send_email` 바인딩은
계정에 등록·검증한 주소로만 보낼 수 있어서, 임의의 댓글 작성자에게는 쓸 수 없다.
그래서 Resend 를 HTTP 로 부른다 — Workers 에서 SDK 나 변환 계층 없이 fetch 한 번이다.

- 발송은 `waitUntil` 로 응답 뒤에 돌린다. 메일 서버가 느리다고 댓글 등록이 늦어질 이유가 없다.
- 키가 없으면 조용히 건너뛴다. 로컬 개발과, 아직 도메인 인증을 안 한 운영에서
  댓글 기능 자체가 막히면 안 된다.
- 실패해도 예외를 던지지 않는다. 로그만 남긴다.
- 수신자 주소는 로그에 남기지 않는다.

## 대표 호스트를 www 로 고정

`namsu.kim` 과 `www.namsu.kim` 둘 다 같은 Worker 의 커스텀 도메인이다.
둘 다 200 을 주면 검색엔진이 같은 글을 두 주소로 세고, canonical 과 사이트맵이
쓰는 `www` 쪽으로 평가가 모이지 않는다. 그래서 Astro 미들웨어가 apex 요청을
`www` 로 넘긴다(GET/HEAD 는 301, 그 외는 메서드를 보존하는 308).

Cloudflare 대시보드의 Redirect Rules 로도 같은 일을 할 수 있고 그쪽이 Worker 를
아예 깨우지 않아 더 싸다. 미들웨어를 고른 이유는 설정이 저장소 안에 남아
배포와 함께 움직이기 때문이다. apex 로 들어오는 트래픽 자체가 많지 않다.

## 알려진 제약

- **FTS5 trigram 은 2글자 이하 질의를 매칭하지 못한다.** 쿼리 계층에서 `LIKE` 스캔으로 폴백한다.
  글이 수천 개를 넘어가면 재검토가 필요하다.
- **`schema.ts` 와 손으로 쓴 마이그레이션이 갈라질 수 있다.**
  drizzle-kit 이 트리거·가상 테이블·부분 인덱스를 모르기 때문이다.
  스키마를 고칠 때 이 파일들도 같이 봐야 한다.
- **마이그레이션은 drizzle-kit 과 손 편집을 섞어 쓴다.** 테이블·컬럼 변경은
  `pnpm db:generate` 가 만들고, 트리거와 FTS5 는 손으로 쓴다.
  `wrangler d1 migrations apply` 는 디렉터리의 `.sql` 을 이름 순으로 전부 실행하고,
  drizzle-kit 은 `meta/_journal.json` 과 스냅샷만 본다. 두 쪽이 보는 것이 다르므로
  **저널의 `idx` 와 파일 이름의 번호를 항상 맞춰 둔다.** 손으로 쓴 마이그레이션도
  스냅샷 자리를 채워야 다음 `db:generate` 가 번호를 겹쳐 쓰지 않는다.
- **D1 무료 플랜은 하루 500만 row read / 10만 row write** 한도가 있고 초과하면 쿼리가 실패한다.
  Workers Paid 로 올리면 사실상 해제된다.
- **마이그레이션은 배포 워크플로가 실행하지 않는다.** 컬럼을 추가하는 변경은
  배포 전에 `pnpm db:migrate:remote` 로 먼저 적용해야 한다.
  순서가 뒤집히면 새 코드가 없는 컬럼을 읽어 500 이 난다.
